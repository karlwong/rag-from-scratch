# Experiment backlog

Prioritized by expected leaderboard gain, implementation effort, and hidden-test overfitting risk.

## Priority 0: done / immediate baseline infrastructure
- [x] Build a reproducible profiler for `train.csv` and `test.csv`.
- [x] Write benchmark-specific forensics and taxonomy docs.

## Priority 1: highest-value next steps

### 1. Implement exact family router
**Expected gain:** very high  
**Effort:** low  
**Overfitting risk:** low

Why:
- The six families expose nearly exact lexical markers.
- A deterministic router should remove most prompt-understanding uncertainty immediately.

Deliverable:
- `scripts/build_router.py` with top-level family routing and equation sub-routing.

### 2. Implement deterministic solvers for Roman, unit, and gravity
**Expected gain:** very high  
**Effort:** low  
**Overfitting risk:** low

Why:
- These three families together cover 4,767 / 9,500 rows.
- They appear structurally homogeneous and algorithmic.
- There is little evidence that model training is needed for them.

Checks:
- Roman outputs match canonical uppercase Roman numerals.
- Numeric outputs preserve exactly two decimals.

### 3. Reverse-engineer the text cipher generator
**Expected gain:** high  
**Effort:** medium  
**Overfitting risk:** medium-low

Why:
- This family is large (1,576 rows) and likely solvable without fine-tuning.
- The small global vocabulary and repetitive grammar suggest constrained decoding is feasible.

Concrete experiments:
1. infer whether the cipher is monoalphabetic substitution, affine substitution, keyboard permutation, or another bijection class,
2. recover the benchmark lexicon and tag words by role (subject / verb / adjective / location / preposition),
3. validate whether per-prompt decryption can be done from the demonstrations alone.

### 4. Taxonomize `equation_transform` more deeply
**Expected gain:** high  
**Effort:** medium-high  
**Overfitting risk:** medium

Why:
- This is the most heterogeneous family.
- It is the main blocker to a solver-first architecture.

Concrete experiments:
1. cluster numeric-expression prompts by induced operator behavior,
2. cluster punctuation-string prompts by edit pattern (delete, substitute, duplicate, reverse, index-select, etc.),
3. test a small DSL/program-synthesis search against subsets of the family.

## Priority 2: solver-oriented experiments

### 5. Bit-transform operator search
**Expected gain:** medium-high  
**Effort:** medium-high  
**Overfitting risk:** medium-low

Why:
- The family is large and structured.
- The prompt text explicitly hints at the allowed operator library.

Concrete experiments:
- build a candidate DSL with rotate / shift / XOR / AND / OR / NOT / majority / choice,
- fit shortest consistent programs to each prompt,
- measure whether one-step or two-step compositions explain most rows.

### 6. Output normalization and extraction harness
**Expected gain:** medium  
**Effort:** low  
**Overfitting risk:** low

Why:
- This benchmark is exact-match heavy.
- Errors such as `19` vs `19.00`, lowercase Roman numerals, or stripped leading zeros will lose solved items.

Concrete deliverable:
- shared formatting validator for each family, with optional boxing policy if needed by final inference prompt.

## Priority 3: only after solver evidence is exhausted

### 7. Prompting experiments with family-specific inference templates
**Expected gain:** medium  
**Effort:** low-medium  
**Overfitting risk:** medium

Focus:
- terse answer-only prompting,
- explicit output-shape constraints,
- optional self-check for decimal precision or binary width.

### 8. Minimal LoRA only if solver coverage stalls
**Expected gain:** unknown  
**Effort:** medium-high  
**Overfitting risk:** high

Current stance:
- **not recommended yet**.
- The current evidence does not justify jumping to fine-tuning because most benchmark mass appears to be generated by deterministic or near-deterministic rules.

Use LoRA only if:
- equation and bit families retain substantial unsolved residue after explicit solver work,
- prompting alone cannot stabilize text decryption,
- we can construct benchmark-faithful synthetic data from inferred generators.

## Fallback options if hidden test shifts
1. Keep a generic LM fallback path for any prompt the router marks as low confidence.
2. Add answer-schema validators so fallback generations still obey output format.
3. Log solver confidence scores to enable selective routing rather than all-or-nothing solver usage.
